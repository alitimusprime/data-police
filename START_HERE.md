# Start Data Police

These instructions target your Windows PC, Python 3.12 and Ubuntu WSL distribution at `D:\WSL\Ubuntu`. The project does not change boot settings, relocate WSL or install anything onto C by itself.

## 1. Put the project on D

Download `Data-Police-v0.1.0.zip` into `D:\Projects`. The archive contains a `data-police` directory.

Open **Ubuntu**, then run:

```bash
mkdir -p ~/projects
python3 -m zipfile -e /mnt/d/Projects/Data-Police-v0.1.0.zip ~/projects
cd ~/projects/data-police
```

Use this command once into a new destination. Your WSL home directory is physically on D because the Ubuntu virtual disk is at `D:\WSL\Ubuntu`. This keeps PostgreSQL files on a Linux filesystem, where container ownership and file locking work properly. Avoid running PostgreSQL bind-mounted data directly from an NTFS `/mnt/d` directory.

Open the folder from VS Code with `code .` if you have its WSL integration, or view it in Windows through the Ubuntu share. The project does not require you to move it to C.

## 2. Check Docker storage and integration

Start Docker Desktop. Confirm its Linux container data location is on D and that **Settings > Resources > WSL Integration** enables your Ubuntu distribution. Docker Desktop manages its own storage separately from Ubuntu. Do not assume that a D-backed Ubuntu distro also moves Docker's images.

In Ubuntu:

```bash
docker version
docker compose version
python3 --version
```

Both a Docker client and server must appear. If `docker version` cannot reach the server, start Docker Desktop and check WSL integration before continuing. These commands inspect your setup; they do not migrate storage or change C.

## 3. Start the complete stack

From `~/projects/data-police`:

```bash
python3 scripts/bootstrap.py
docker compose up --build -d
docker compose ps --all
```

Bootstrap creates a private `.env` with unique local credentials. Save the printed password in your password manager. Running bootstrap again preserves the existing file and password.

The first build downloads pinned Python and JavaScript dependencies. Startup order is PostgreSQL and Redis, migrations and provider API, 12 baseline batches, then the application, workers and schedulers. Give the first startup time to finish. Do not keep resetting the databases while it builds.

Use these read-only commands to see progress:

```bash
docker compose logs --tail=60 seed
docker compose logs --tail=60 api worker monitor
docker compose ps --all
```

Expected service state:

| Service | Expected result |
| --- | --- |
| postgres, redis, demo-api, api | Running and healthy |
| worker, monitor, dagster-web, dagster-daemon | Running |
| permissions, migrate, seed | Exited with code 0 after completing their work |

Open **http://localhost:8000** in Windows. Email: `admin@datapolice.local`. Password: the value generated by bootstrap. This application intentionally requires sign-in; a `401` from a protected API before signing in is expected.

Dagster is at **http://localhost:3001**. Keep that administrative interface on your own machine. Product API documentation is at **http://localhost:8000/api/docs** after sign-in.

## 4. Take the first product tour

1. **Overview:** verify that the 19 datasets are measured and the initial estate is healthy.
2. **Datasets:** search `raw_payments`, open it, and inspect Schema & profile, Quality and Dependencies.
3. **Failure lab:** select Country code change and click Inject & run. Wait for the new run to succeed.
4. **Incidents:** open the new incident. Read the source ranking, score contributions and evidence records.
5. Click Generate investigation. Inspect the measured Pakistan revenue failure, inference, hypotheses and recommended actions. The built-in report works without an AI key.
6. Trace the downstream path in Lineage. Observed affected datasets have actual anomalies; other reachable datasets are only potentially affected.
7. Return to Failure lab and click Restore healthy source. Run the pipeline twice, waiting for each run to finish. The incident should resolve after those two clean runs.

The lab changes one scenario at a time. API outage and removed-field scenarios intentionally fail a pipeline. Paused ingestion intentionally produces no new Parquet profiles; the independent freshness monitor raises stale-data findings after 180 seconds by default.

## 5. Stop and resume safely

Stop services while preserving data:

```bash
docker compose stop
```

Resume an existing stack:

```bash
docker compose up -d
```

The bind-mounted `runtime` directory contains your history. Do not delete it to fix a login problem. A restart can show freshness findings because no batches were produced while the stack was stopped. New clean runs verify recovery.

## Lighter local profile

Use this path when you want to exercise the product before Docker is available. It uses SQLite and a local worker; it does not exercise PostgreSQL or Redis. In Ubuntu, Python 3.12 or newer is required. Windows Python and WSL Python are separate installations.

```bash
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
python scripts/bootstrap.py
python scripts/start_local.py
```

The ZIP already contains `web/dist`, so Node is not needed to run this profile. If you are using a source-only Git checkout, build the interface first with Node 22:

```bash
cd web
npm ci
npm run build
cd ..
python scripts/start_local.py
```

Open the same http://localhost:8000 address and use the same generated administrator credentials. Ctrl+C stops the API, source provider and scheduler together. For a controlled demonstration without automatic pipeline scheduling, use `python scripts/start_local.py --no-schedule`; manual runs remain available. The independent freshness loop is also stopped by this flag, so the paused-ingestion scenario requires the normal launcher or an explicit freshness command.

Do not run the local and Docker profiles on port 8000 simultaneously. Their database histories are separate: local databases live in `runtime/*.db`, while the Docker app uses `runtime/app` plus `runtime/postgres` and `runtime/redis`.

## If something does not work

| Symptom | Next action |
| --- | --- |
| Browser cannot connect | Check `docker compose ps --all`, then `docker compose logs --tail=60 api seed`. Wait for seeding to finish. |
| Login rejected | Open your local `.env` and use its current `DP_ADMIN_EMAIL` and `DP_ADMIN_PASSWORD`. Bootstrap does not reset an existing password. |
| Login succeeds but protected calls return 401 | Use one hostname consistently. Cookies for `localhost` and `127.0.0.1` are separate. Keep `DP_COOKIE_SECURE=false` for local HTTP and restart the API after config changes. |
| Seed exits with failure | Check `demo-api` and `migrate` logs. Correct the startup issue, then rerun `docker compose up -d`. Failed initial baseline attempts are retried; successful ones are preserved. |
| Source test fails | Check the provider service, configured database URL or feed directory. Do not paste connection strings into public issues. |
| Run remains queued | Check worker and Redis health, then monitor logs. The saved run remains available for redelivery. |
| Permission denied on runtime | Ensure the project is inside Ubuntu's Linux filesystem. Check the `permissions` service result. Do not apply broad recursive permissions to your home or drive. |
| Dataset says stale after restart | Restore the healthy source and allow two successful runs. History is preserved across downtime. |
| Port 8000 or 3001 is busy | Stop the other application using that port, or adjust the Compose host binding and allowed origins together. |

The build workspace verified the application with SQLite, real HTTP, a real Redis worker and Chromium. It could not run Docker or native PostgreSQL. Treat the first successful Compose startup on your machine as the remaining runtime acceptance check. See [docs/VERIFICATION.md](docs/VERIFICATION.md).
